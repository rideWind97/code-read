# React 为什么要有合成事件

React 设计合成事件（SyntheticEvent）主要有以下原因：

1. 兼容性统一
- 不同浏览器原生事件在属性命名、事件对象能力、边界行为上都可能有差异。
- React 用 `SyntheticEvent` 做一层标准化封装，开发者拿到的事件对象接口更一致（如 `target`、`currentTarget`、`preventDefault`、`stopPropagation`）。
- 这样可以减少“某浏览器可用、某浏览器异常”的兼容代码。

2. 事件委托 + 更低监听成本
- React 不会给每个节点都绑一个原生监听器，而是把同类事件集中托管，再分发到对应组件。
- 这样能显著减少监听器数量，降低内存和注册成本，尤其在大量列表节点场景更明显。
- 注意：React 17 起，委托挂载点从 `document` 调整为“当前 React 根容器”，让多 root 共存和渐进升级更安全。

3. 与渲染调度深度配合
- 合成事件不仅是“兼容层”，也是 React 调度系统的入口之一。
- 事件触发后的状态更新会被 React 感知并进入优先级调度流程（如离散事件、连续事件等），以保证交互响应性。
- 在 React 18 中，自动批处理能力扩展到更多异步场景，但事件系统仍是高频更新的重要来源。

4. 跨平台抽象能力
- React 希望上层组件编程模型尽量稳定，不强耦合某个宿主环境的事件细节。
- 合成事件这层抽象有利于把“组件逻辑”与“平台事件实现”解耦，便于迁移与扩展。

5. 可控的事件行为语义
- React 支持捕获和冒泡阶段处理（如 `onClickCapture` / `onClick`），并统一了分发顺序语义。
- 某些原生不冒泡的事件，React 会通过内部机制模拟出更统一的处理体验（具体事件类型有差异）。
- 这种可控性让框架可以在升级时持续优化事件系统，而不把复杂性暴露给业务代码。

## 常见误区澄清

- “合成事件比原生事件慢很多”  
  通常不是瓶颈。多数性能问题来自频繁重渲染或复杂计算，而不是事件封装本身。

- “事件对象会被立刻清空，异步里不能用”  
  这是旧版本（事件池）常见认知。React 17 起已移除事件池，通常不再需要 `event.persist()`。

- “React 18 没有合成事件了”  
  不正确。React 18 仍有事件系统，只是批处理和调度能力更强，覆盖场景更广。

## 总结
合成事件不只是“兼容浏览器差异”的薄封装，而是 React 事件分发、更新调度和跨平台抽象的重要基础层。它通过统一接口、事件委托和可控语义，降低了开发复杂度，并为性能优化与框架演进提供了空间。
